1K8s 组件协同：一切围着 apiserver 转

组件之间互不通信；apiserver 是唯一能读写 etcd 的组件；一切靠 watch 事件驱动，不轮询

kubectl / CI / Dashboard　（客户端）
↓
HTTPS 请求 / List-Watch 长连接
kube-apiserver
认证 → 鉴权 → 准入控制 → 校验 → 读写 etcd　·　所有组件的唯一对话对象
⇅⇅⇅
etcd
唯一数据库，只有 apiserver 读写
Raft 多数派 · RPO=0
提供 watch，是事件驱动的源头
kube-scheduler
watch 未调度的 Pod
Filter（能不能去）→ Score（哪个更好）
写回 .spec.nodeName —— 只决策，不起容器
kube-controller-manager
一堆控制器的集合，跑 reconcile 循环
Deployment 控制器 → 生成 ReplicaSet
ReplicaSet 控制器 → 生成 Pod
Node 控制器、Endpoint 控制器……
⇅
Worker Node（每台机器上都跑这两个）
kubelet　节点的执行者
watch 到分给本节点的 Pod → 通过 CRI 调 containerd：拉镜像 → sandbox → initContainers → 业务容器； 执行 liveness/readiness 探针；持续把容器状态回写 Pod.status
kube-proxy
watch Service / Endpoints 变化 → 刷新本机 iptables / ipvs 规则， 让 Service 的流量能落到 Pod 上
三条铁律（面试讲协同的核心）
① 组件之间零直连：scheduler 和 kubelet 从不直接通信，全靠 apiserver 中转 —— 所以挂掉一个不阻塞别人
② 只有 apiserver 碰 etcd：整个集群的读写入口唯一，权限、审计、准入都在这里收口
③ 全部 watch 驱动 + 声明式对账：没人"指挥"，每个组件只看自己关心的对象，变化就干活
