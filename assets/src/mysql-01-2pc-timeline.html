1MySQL 两阶段提交：写入时序与崩溃点

顺序不能换：redo prepare → binlog → redo commit。判据是 binlog 是否完整

① Prepare 阶段 —— 先把物理修改钉住
redo log buffer ──► redo 文件 ──► fsync 落盘 ──► 打上 prepare 标记
✂ 崩溃点 A：redo 说"我在准备"，binlog 里什么都没有 → 回滚
② Commit 阶段 a —— 再写逻辑日志，这是最终判据
binlog cache ──► binlog 文件 ──► fsync 落盘 ──► 末尾带 XID event
✂ 崩溃点 B：binlog 已经完整了 → 恢复时判 提交
③ Commit 阶段 b —— 补上"定论"的标记
redo 文件 ──► 写入 commit 标记 ★ 不必立刻 fsync
✂ 崩溃点 C：redo 已有 commit 标记 → 直接提交（连 binlog 都不用看）
为什么第 ③ 步可以不 fsync
因为 prepare 已经落盘、binlog 也已经完整落盘。万一崩在这，恢复时看到"prepare + binlog 完整" 照样判提交。用 binlog 的完整性，替代了对 commit 标记落盘的依赖 —— 这就是这套设计的精髓，也是它省下一次 fsync 的地方。
