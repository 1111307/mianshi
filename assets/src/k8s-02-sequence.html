2从 kubectl apply 到流量进来：一条命令的接力

你只写「期望」，下面这串接力负责把它变成现实；每一步都是 watch 驱动

1
kubectl
apply -f deployment.yaml：期望 3 副本，只提交这份期望，不指定跑在哪台机器
↓
2
kube-apiserver
认证 → 鉴权 → 准入 → 校验 → 对象写入 etcd（此刻集群里多了个 Deployment 对象，还没有任何 Pod）
↓
3
Deployment 控制器
watch 到新 Deployment → 对账：期望 RS 数 = 1，实际 0 → 创建 ReplicaSet（把 Pod 模板和副本数传下去）
↓
4
ReplicaSet 控制器
watch 到新 RS → 对账：期望 3 个 Pod，实际 0 → 创建 3 个 Pod，此时 .spec.nodeName 为空（PENDING，未调度）
↓
5
kube-scheduler
watch 到「未调度的 Pod」→ Filter 剔除资源不足/亲和性不符的节点 → Score 打分 → 写回 nodeName（Binding）。只写一个字段，不碰容器
↓
6
kubelet（选中节点）
watch 到「分给本节点的 Pod」→ CRI 拉镜像 → 建 sandbox → 跑 initContainers → 起业务容器
↓
7
kubelet
readiness 探针通过 → 回写 Pod.status = Running → apiserver → etcd（这一刻状态才和期望对齐）
↓
8
kube-proxy
watch 到 Endpoints 更新 → 刷本机 iptables / ipvs 规则：Service 的 VIP 有了真实后端
↓
9
流量进来
客户端访问 Service → 转发到 Pod → 整个链路打通
关键：期望状态 vs 实际状态是两条路
spec 期望，由命令面（kubectl / 控制器）写入　·　 status 实际，由节点面（kubelet）回报
控制器做的事只有一件：不断把 status 扳回 spec。所以任何一步失败都不用管，下一轮对账会重试。
为什么叫「声明式」
你说的是要什么（3 个副本），不是怎么做（在哪台机器起、怎么拉镜像）。
于是扩容、滚动更新、故障自愈都变成同一件事：改期望值，让循环自己收敛。
